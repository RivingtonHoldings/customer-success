# Port to Intercom

The last step of the article pipeline. An article has been drafted or rewritten, reviewed by the team in Notion, and scored; this skill carries it into Intercom, where members and Fin actually read it, and closes the Notion row. Every MLS in `docs/help-center/mls-registry.md` is a peer: the same row produces one Intercom record per MLS, each carrying that MLS's screenshots and videos (see Per-MLS differences).

This skill owns transfer mechanics only. It does not rewrite, score, or re-review: if the draft is not ready, stop and say so rather than fixing it here. The policy it answers to is `.claude/skills/article-draft/references/intercom-push.md` and the write-rules ladder in the root `CLAUDE.md`.

## Inputs

- **The article** (required). A Notion page URL from the Perchwell Help Center Database [Sep 2026], an Intercom admin URL, an article title, or a mirror path under `docs/help-center/`.
- **Mode hints** (optional). "dry run" converts and diffs but writes nothing. "preflight" checks the preconditions and stops. "new article" forces rung 2 when no live article exists.
- **Target** (required). An MLS slug from the registry (`baldwin`, `crmls`, or any MLS added later), given as "port to CRMLS", "CRMLS", or `--mls crmls`. The same Notion row produces a separate Intercom record for each MLS, so the skill ports to one MLS per run. If no target is given, ask which MLS; never assume one.

## Workflow

1. **Resolve the Notion row.** Fetch the page and read `Article Name`, `Article Status`, `Article Review Status`, `MLS` (multi-select of the registry's display names), `Collection`, `Roles`, and the target MLS's `Intercom URL`, `Visual Status`, and `Video Status` fields, whose names come from the registry. The data source is `3d18b9e0-1438-80cc-ab0f-000bf0fc1389`. The property was renamed from `MLS/AOR` and its CRMLS option from `CRLMS All` before November 4, 2026; older docs that use the old names are describing this field.

   Also read the article's media record, `docs/help-center/media-record/<Tracker ID>.json`, when it exists (format in that folder's `README.md`). It is a receipt of the last push, never a source for content; Notion is the source, and where the two disagree Notion wins. No file means the article has not been pushed under this scheme, and step 5 treats it as a first publish.

2. **Resolve the Intercom article ID.** Prefer the target MLS's `Intercom URL` field on the Notion row and take the number from the slug (`.../articles/11002620-universal-search-bar` is article **11002620**). With no URL, call `search_articles` on the title. **Never treat a number from an Intercom admin URL as the article ID.** An admin URL reads `activeContentId=11821319`, and that is the *content ID*, the number Fin cites, not the API ID. To go from one to the other, search by title and match the `content_id` field. Passing a content ID to `get_article` returns `not_found`, which is the good case; the bad case is that it matches some other article.

3. **Check the preconditions** for the target MLS. Report each as pass or fail and **stop on any failure**, saying why in plain words.

   - **Status.** `Article Status` is `Ready to Transfer` or `Live in Intercom`. `Draft`, `New Article Request`, and `Deprecated` are never pushed. A `Draft` row whose URL field for the target MLS is already filled gets this message: "This row is Draft, but its <MLS> article is already published. Set the row to Ready to Transfer to publish edits." The skill never changes the status to get past it.
   - **Review.** `Article Review Status` is `Review Finished` or `Complete`. This is a required check, not proof that edits made since the last publish were reviewed or approved, because the field does not reset when someone edits. The teammate's confirmation of the diff in step 6 is the approval.
   - **MLS.** The row's `MLS` field contains the target MLS.
   - **Update or create.** The target MLS's URL field filled means **update**; empty means **create**. A filled field is never a create. Before a create, call `search_articles` with the target help center's ID on the row's title (a trailing MLS suffix such as ` (CRMLS)` removed) and on any old title in its QA file. A same-titled article stops the run: ask whether to link it to this row or create anyway. Never create silently from an empty field.
   - **Update identity.** On an update, `get_article` must return the article; its title must equal the row's `Article Name` with a trailing MLS suffix removed, or the title in the article's media record for that MLS, or the title in the newest `docs/help-center/changelog.md` line for that article and MLS (a line whose subject is the article: the title followed by its ID in parentheses, not a line that only mentions the ID as a link target); and its `parent_ids` must include a collection owned by the target MLS's help center in `docs/help-center/collections.md`. Any mismatch stops the run and names both sides.
   - **Collection for a create.** `collections.md` has a collection owned by the target MLS's help center whose name matches the row's `Collection` (a sub-collection matches on its full `Parent / Child` name). A missing match is a failure that names the collection.
   - **Readiness.** Read the table headed "MLS publishing readiness" on the Help Center Production Tracker (page ID in the registry). `No` blocks a create and never an update; `Paused` blocks both. A missing row, a blank, or an unreadable table counts as `No` for a create and never blocks an update, and the report says when the table could not be read.
   - **The rest of `intercom-push.md`.** Pushes are on, the mirror is trusted, the collection is identified so `parent_id` is known, and an `author_id` is known for a create.

   Report the target MLS's `Visual Status` and `Video Status` as well, never gating: a `Blocked` or `Not Started` value changes what the body carries, not whether it ports.

4. **Check who the article actually reaches.** Call `get_article` and read **`parent_ids`**, then map every ID through `docs/help-center/collections.md` to its owning help center. Report the full list before the diff.

   **Do not decide this from the mirror.** The mirror is the wrong instrument: it covers the registered MLSs only, because the default help center (NYC and brokerages) is deliberately not mirrored. An article in a default collection looks single-audience in the mirror and is not. This is exactly what happened on the Dashboard Overview port, 2026-09-18: the mirror recorded one collection, `parent_ids` held two, and the second was the default help center. The rewrite reached an audience outside the project's scope and nothing in the repo would have shown it.

   When more than one help center is in the list, say so plainly and check every cross-link: a link into one help center is wrong for readers of the other. Name those links and let the teammate decide. Do not silently rewrite or drop them.

5. **Convert the body to Intercom HTML** using `references/intercom-html.md`. The title and the `**Description:**` line leave the body and become the `title` and `description` fields.

   **Keep only this help center's screenshots.** A caption that starts with an MLS's display name and a bar, such as `Baldwin |` or `CRMLS |`, marks an image for that MLS only, and a placeholder labeled `(Baldwin)` or `(CRMLS)` likewise. Take the target help center from step 4: keep the unlabeled images and the ones labeled for that help center, strip the label, and drop the rest. List what was dropped in the diff, so a reviewer can see each step still has its image. If step 4 found the article in more than one registered MLS's help center and the draft has labeled images, stop: one article cannot show each MLS its own screenshot, and keeping either set shows the wrong one to the other MLS. Ask the teammate whether to split the article or pick one image per step.

   **Classify every image and video against what was last published.** Give each kept item an identity as `docs/help-center/media-record/README.md` defines it: the file ID for an uploaded Notion image, the URL path (signature removed) for an external image, the Loom or Arcade URL for a video. Never use a block ID or a signed URL. Then, per item:

   - **Unchanged.** Same identity as the media record for this MLS (or, with no record yet, an external image whose URL path equals the live body's, or a block that `notion-get-version-changes` shows untouched since the last time this MLS's media was pushed from Notion, as defined under "Where history starts" below). Keep the Intercom copy and its `width` and `height`.
   - **Replaced or added.** A different identity in the same position, or no match in the record. Re-host the current Notion image (see `references/intercom-html.md`) or embed the current video link.
   - **Removed or moved.** In the record but gone from Notion, or at a different position. Say so in the diff.
   - **Cannot be verified.** An uploaded image with nothing to compare against: no record, no usable history, and not an external link. Never silently reuse the old screenshot. List it under Needs your attention, and on confirmation re-host the current Notion image.

   **Where history starts.** Read Notion's history from the last time this MLS's media was pushed from Notion, never from the live article's `updated_at`. An update that only swapped links or edited text built from the live body keeps the images already in Intercom, so its date says nothing about them (found November 18, 2026: Universal Search Bar CRMLS had a screenshot replaced in Notion before a links-only update, and the old image stayed live). With a media record, start at its `published_on` only for items it holds a verified identity for. With no record, start at the date of the newest changelog line for this MLS that created the record or re-ported the body from Notion, and skip lines that only swapped links or edited a draft; if none exists, start at the article's `created_at`. `notion-get-version-changes` reads at most seven days per call, so call it again for each earlier window until the start is covered. An item whose history cannot be read back that far is Cannot be verified.

   Cross-check the classification against `notion-get-version-changes` since that start. A block history shows as replaced that the identity comparison calls unchanged, or the reverse, goes under Needs your attention. A replaced image shows in history as a removed block plus an added one, so read it together with the identity.

   **Flag caption forms and label conflicts.** Under Needs your attention, list a caption that starts with an MLS's display name but not in the standard `<MLS> |` form (such as `CRMLS:`), which this skill would otherwise treat as unlabeled; a label that conflicts with the filename or the MLS's Visual Status or Video Status; an unrecognized label; and a slot whose identity and label both changed. Whitespace around the `|` is fine and is not flagged. Unlabeled images stay shared and never trigger this. Unlabeled videos follow the registry's rule (Per-MLS differences).

   **Replace every link to a Notion page with the Intercom article it stands for.** Drafts link sibling articles as Notion page mentions (`<mention-page url="…">`) or `app.notion.com` / `notion.so` URLs while those siblings are still drafts. Members cannot open a Notion page, so none may reach Intercom. For each one:

   - Fetch the linked page. If it is a row in the Perchwell Help Center Database [Sep 2026], take its `Intercom URL`. If that is empty, find the Intercom article the row will replace: the `Intercom article ID` in its QA file under `workstreams/help-center-overhaul/qa/`, or `search_articles` on its `Article Name` and old title.
   - Call `get_article` on that ID. Use the public `url` it returns, with the target help center from step 4 in the path (`/baldwin/en/` or the target MLS's path from the registry), never a bare `/en/` link.
   - Keep the row's `Article Name` as the link text. If the target has not been ported yet, its live title still differs; say so in the report, because the link text matches only once that article ports.
   - Sort each link before the diff: **resolved** (the linked row's URL field for the target MLS is filled and that article is published), **shared** (the linked record already sits in a collection owned by the target MLS's help center; label it "shared article"), or **missing** (no article for the target MLS, or one that is still a draft in Intercom).

   **A missing link is a decision for the teammate, one link at a time.** Explain it in plain words: "The CRMLS version of Universal Search Bar links to Search FAQ in the section 'Find several listings at once.' Search FAQ has no CRMLS article yet, so there is nothing in the CRMLS help center to link to." One missing link never blocks the rest of the update. The teammate chooses for that link:

   1. **Stop.** Nothing is written for this MLS.
   2. **Publish without the link.** The link text stays as plain text and everything else publishes.
   3. **Approve a named exception.** The teammate names the exact destination (title, MLS, URL). Repeat it back with a warning that readers of the target MLS would leave their own help center, and take a yes for that link alone. Only the one named destination is used. "Approve all" is not accepted.

   Nothing is substituted automatically, in either direction, and no Notion URL is ever emitted. Read `docs/help-center/link-exceptions.md` first: an Active exception for this article, MLS, and link text is listed again as a reminder, and when the missing article now exists for the target MLS, offer to replace the exception with the correct link instead. If the named destination has changed, ask again.

   List every replacement in the diff (link text, Notion page, Intercom URL) and every missing link with the choice made. Added October 23, 2026, after the Search collection review found Notion links in five articles; the per-link decision replaced the old stop-or-keep rules in the November 2026 `/publish` change.

6. **Diff and confirm.** When `/publish` called this run, its plain-language preview has already been shown and the link decisions taken; go straight to the diff. Run on its own, open with a short plain-language summary in the same shape (what changed in text, screenshots, video, and links, and anything needing attention) before the diff. Fetch the live body with `get_article` and show the full before-and-after in the conversation: title, description, then the body section by section. Ask for confirmation **for this one article**. "Yes to all" is not accepted, and a batch of articles is confirmed one at a time.

   **Edited in Intercom since the last publish.** On an update, compare the live article's `updated_at` with the `intercom_updated_at` in the media record for that MLS. If the live value is later, someone edited the article in Intercom after the last push here. With no media record yet, fall back to the date of the newest `docs/help-center/changelog.md` line for that article and MLS (matched as in step 3): if `updated_at` falls on a later day, or no such line exists, someone may have edited the article in Intercom after it was last published here. Say so before the diff, in plain words (for example, "Edited in Intercom on Nov 3, after the last publish on Nov 1; pushing replaces that edit"), show what would be replaced, and ask a **separate confirmation** that comes first and stands alone. A yes to the normal confirmation does not cover it. If the teammate declines, nothing is pushed for that record.

   **Diff against `get_article`, never against the mirror.** The mirror holds the page Intercom renders for a reader, and the rendering differs from the stored HTML: a cross-link stored as `/en/` is served as `/baldwin/en/`, so the mirror shows a path the article does not contain. Diffing the Notion draft against the mirror on 2026-09-23 produced a seven-link regression that did not exist, and the "fix" for it was an unrequested change to a reviewed page. The same trap as step 4's, one field over.

7. **Push.** On an update call `update_article` with `id`, `body`, and `title` or `description` only when they changed. On a new article call `create_article` with `state: "draft"` and the `parent_id` and `parent_type` of the target MLS's collection from step 3, read from `collections.md`. Nothing else in either call. See the Rules.

8. **Verify.** Call `get_article` and confirm `state` is unchanged and `parent_ids` still holds every collection it held before. Then open the public URL and check what a member sees: every image loaded, the video playing, and no blank gaps from whitespace between block tags. Expect the stored HTML to differ from what was sent in the ways `references/intercom-html.md` lists under "What Intercom changes on save"; anything beyond that list is a real defect.

9. **Close the loop.** Prepend a line to `docs/help-center/changelog.md` under the header, newest first: date, MLS, article title, what changed, who confirmed. In Notion, fill the target MLS's URL field with the public URL under that MLS's path. Set `Article Status: Live in Intercom` when the row was `Ready to Transfer` before this push; a row already `Live in Intercom` stays as it is. Write the media record: `docs/help-center/media-record/<Tracker ID>.json`, only the target MLS's entry, with the article ID, the title, the `updated_at` from the `get_article` call in step 8, the Notion page's last-edited time read in step 1, and every image and video the pushed body carries (identity, label, position, and the Intercom URL it became). Record a Notion identity only for an item re-hosted from Notion in this push or verified unchanged under step 5; an item kept from the live body without that verification gets the identity `unknown`, so a later run never mistakes a stale image for a current one. Leave other MLSs' entries as they are. If the push made a named exception, add or update its row in `docs/help-center/link-exceptions.md` (article, MLS, link text, section, destination, who approved, date, status Active); mark an exception Replaced when this push swapped in the correct link. Run `/sync-help-center` with a **fresh work folder**, then run it again and confirm the second run reports zero changes.

   Then grep the rebuilt mirror file for one fact you just changed and confirm it is there. The counts and the clean second run can both look right over a stale body, so this is the only check that proves the mirror caught the push.

10. **Report.** The article ID and public URL, what changed in title, description, and body, the changelog line, the Notion row's new status, the mirror files the sync touched, and anything left for a human: Fin labels per `docs/standards/fin-labeling.md`, MLS audience, new screenshots or video, any cross-link flagged in step 4, every missing link and the choice made, every exception still Active, and every item under Needs your attention from step 5.

## Per-MLS differences

Every MLS in `docs/help-center/mls-registry.md` is a peer. One Notion row produces one Intercom record per MLS in its `MLS` field, in that MLS's help center, in the collection with the same name as the row's `Collection`. The target MLS's URL field on the row points at its record. A port to one MLS never writes another MLS's record. The two-record design was decided with Leo on November 4, 2026 (the decision record is in `workstreams/help-center-overhaul/docs/decisions.md`) and generalized to every registered MLS in the November 2026 `/publish` change.

Each numbered step above applies to the target MLS with these details:

- **Step 2.** Read the row's other MLS records from their URL fields as well when they exist: a stored body supplies CDN URLs for unlabeled images that are already hosted, and its `parent_ids` tell you whether that record still sits in a collection owned by the target MLS's help center.
- **Step 4, what a create replaces.** On a create, call `search_articles` with the target help center's ID on the article's title and any old title in its QA file, and `get_article` on each hit. Report a **retire list**: legacy records in that help center with the same subject, and another MLS's record itself when its `parent_ids` still include a collection owned by the target MLS's help center. Nothing on the list is touched during the port; see Retirement below.
- **Step 5, convert for the target MLS.**
  - Images: keep unlabeled images and images labeled with the target MLS's display name; drop images labeled for another MLS. When a step's only image is labeled for another MLS, the step carries no image. List every omitted step in the diff and the report so the visual owner can add that MLS's screenshot; do not substitute another MLS's (Leo, November 4, 2026).
  - Videos: a video whose caption starts with the target MLS's display name and a bar is kept, and one labeled for another MLS is dropped, as with images. An **unlabeled** video is kept when the registry says unlabeled video counts for the target MLS (today Baldwin only); for any other MLS it is kept only when that MLS's `Video Status` is `Complete`, and otherwise dropped and logged. Every recording made before November 4 is unlabeled and was shot in Baldwin, so the status field is what says a shared recording also serves another MLS. Never embed another MLS's video as a stand-in (Leo, November 4, 2026).
  - Cross-links: resolve each linked row and sort it as in step 5. A resolved link uses the linked row's URL field for the target MLS. A shared link, whose record's `parent_ids` include a collection owned by the target MLS's help center, is rewritten to `https://support.perchwell.com<the MLS's URL path>articles/<id>-<slug>`. A missing link goes to the teammate's per-link decision in step 5, for every MLS alike; no MLS keeps another MLS's URL by default. Never emit a Notion URL.
  - Image hosting: the scratch-draft method in `references/intercom-html.md`. Reuse a CDN URL only for an image classified Unchanged in step 5, from this MLS's media record or live body, or from another MLS's record for an unlabeled image. Every image labeled for the target MLS that is Replaced, Added, or confirmed from Cannot be verified is new to Intercom and goes through the scratch draft.
- **Step 6.** On a create there is no live body for the target MLS, so show the whole proposed body, plus the title, description, collection name and ID, and the retire list. On an update, diff against `get_article` of the target MLS's record.
- **Step 7.** Create: `create_article` with `state: "draft"`, `parent_id` set to the target MLS's collection ID, and, when the row already has a record in another MLS, that record's exact title and description. Update: `update_article` with `id`, `body`, and `title` or `description` only when they changed. The Rules below apply unchanged.
- **Step 8.** On a create, `parent_ids` holds exactly the one target collection and `state` is `draft`. A draft has no public page, so the member-view check waits until a teammate publishes it; say so in the report.
- **Step 9.** The changelog line starts with the target MLS's display name and, on a create, names the new ID, the collection, the other record it pairs with, what it replaces, and the omitted images and video. Add or update the article's row in `docs/help-center/crmls-port-map.md` when the target is CRMLS (Tracker ID, Baldwin ID, CRMLS ID, CRMLS collection, retire list, image and video gaps, flagged links, retirement status); that file is CRMLS-only today. Then the double sync.
- **Step 10.** The human steps for a create are: publish the draft in Intercom, set the Fin labels with `MLS: <display name>`, remove another MLS's shared record from the target collection if it is still there (name the collection and the record), delete the scratch draft, and come back for Retirement.

**Link pass.** After every article in a collection has a record for the target MLS, run this skill once more over each of them as an update. The only change should be missing links and Active exceptions turning into links to the new records in that MLS's help center. Confirm each article as usual.

**Retirement.** Runs after a teammate publishes the new record, never before, so readers of that MLS are not left without an article. For each legacy record in the target help center on the retire list, call `update_article` with `id` and `state: "draft"` and nothing else. This is a rung 3 change: show the record's title, ID, collection, and current state, take one confirmation for that record, and write one changelog line (precedent: commit 3e4a4d8, two replaced articles unpublished). Deleting a record stays a human step. Another MLS's shared record leaves the target collection by a human in Intercom, because `update_article` takes a single `parent_id` and would drop its other collections; after that, re-probe `collections.md` and re-sync.

## Rules

- **Never set `state: "published"`.** Publishing is a human action inside Intercom. On an update, omit `state` entirely; omitting it leaves a published article published, which is what an update to a live article wants.
- **Never pass `parent_id` or `parent_type` on an update.** They move the article. An article shared between two help centers can lose a collection, and it will not be obvious that it did. Pass them on a create, where there is nothing to lose.
- **Never pass `author_id` on an update**, and say in the report that the byline moved anyway. Unlike `state`, omitting `author_id` does not preserve the original author: Intercom stamps the acting admin. Passing one would only pick a different wrong answer.
- **Never push a row whose status fails step 3, never create from a filled URL field, and never push when the update identity checks in step 3 fail.** A push from a `Live in Intercom` row never changes `Article Status`. The guards against pushing the same article twice over someone else's later edit are the edited-in-Intercom check in step 6 and one confirmation per record.
- **Never hand-edit a file in `docs/help-center/`.** The mirror follows Intercom; only `/sync-help-center` writes there.
- **No conversation, contact, company, or macro writes.** Macros are drafted in the repo and a human creates them in Intercom.
- **Labels and audience are not settable here.** `update_article` cannot touch tags, so existing Fin labels survive a push untouched. Setting them stays a human step.
- **One article, one confirmation, one changelog line.** A release that touches six articles is six of each. A port of the same row to a second MLS is a second article and gets its own.
- **A port never writes to another MLS's record.** Not its body, not its collections. If another MLS's body also needs a change, that is a separate port to that MLS with its own confirmation.
- **Never substitute another MLS's screenshot or video.** A missing asset for the target MLS is a gap in the report, not another MLS's image in its article.
